When a policy has an effect of `REQUIRE_APPROVAL`, Sericin automatically creates an approval request and pauses the agent action until a designated approver responds. This gives your team a reliable checkpoint for high-risk or high-value operations — the agent can keep running autonomously right up until the moment it hits an action that warrants human judgment, at which point control transfers cleanly to a person.

## How approvals work

The approval workflow follows a straightforward sequence:

<Steps>
  <Step title="Policy triggers">
    The policy engine evaluates the agent's action and returns `REQUIRE_APPROVAL`.
  </Step>
  <Step title="Approval request created">
    Sericin creates an approval request record, capturing the full action context: agent ID, action type, payload, and the policy that triggered the request.
  </Step>
  <Step title="Approvers notified">
    Every member of the designated approver group receives a notification via email and/or webhook, depending on your notification settings.
  </Step>
  <Step title="Approver reviews context">
    The approver opens the request in the dashboard (or via API) and sees the complete action payload so they can make an informed decision.
  </Step>
  <Step title="Approves or rejects">
    The approver submits their decision. A comment is optional when approving and required when rejecting, so there is always a recorded reason when an action is blocked.
  </Step>
  <Step title="Agent action proceeds or is cancelled">
    If approved, Sericin releases the paused action and the agent continues. If rejected, the action is cancelled and the agent receives an error response it can handle programmatically.
  </Step>
</Steps>

## Approver groups

Approver groups are named collections of Sericin users who have the authority to approve or reject requests for a given policy. Groups let you route different types of decisions to the right team — for example, `finance-managers` for invoice approvals and `security-team` for access-provisioning requests.

**Create a group in the dashboard:**

<Steps>
  <Step title="Open Approver Groups">
    Navigate to **Settings > Approver Groups** and click **New Group**.
  </Step>
  <Step title="Name the group">
    Enter a name for the group. This value becomes the `approver_group` identifier you reference in your policies.
  </Step>
  <Step title="Add members">
    Add one or more Sericin users to the group.
  </Step>
  <Step title="Set the quorum">
    Set the **quorum** — the minimum number of approvers required before a request is considered resolved. A quorum of `1` means any single member can approve; a quorum of `2` requires two independent approvals before the action proceeds.
  </Step>
</Steps>

You can update group membership and quorum at any time; changes apply to all new approval requests immediately.

## Reviewing and acting on approvals

### Via the dashboard

Go to **Governance > Approvals** to see a list of all pending requests. Each entry shows the agent that triggered the request, the action type, the full action payload, the policy that applied, and how long the request has been waiting. Click any request to review the details and submit your decision.

### Via the API

**List pending approvals:**

```bash
curl -X GET "https://api.sericin.io/v1/approvals?status=pending" \
  -H "Authorization: Bearer $SERICIN_API_KEY"
```

```json
{
  "data": [
    {
      "id": "apr_11223344",
      "agent_id": "agt_xyz789",
      "action_type": "invoice.submit",
      "action_payload": {
        "vendor": "Acme Corp",
        "amount": 24500,
        "currency": "USD"
      },
      "policy_id": "pol_abc123",
      "approver_group": "finance-managers",
      "status": "pending",
      "created_at": "2025-01-15T14:05:00Z",
      "timeout_at": "2025-01-16T14:05:00Z"
    }
  ],
  "total": 1
}
```

The `status` query parameter accepts `pending`, `approved`, or `rejected`. Omit it to return all requests regardless of status.

**Approve a request:**

```bash
curl -X POST https://api.sericin.io/v1/approvals/apr_11223344/approve \
  -H "Authorization: Bearer $SERICIN_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"comment": "Verified against Q1 budget. Approved."}'
```

The `comment` field is optional when approving, but including one provides useful context in the audit log for future reviews.

**Reject a request:**

```bash
curl -X POST https://api.sericin.io/v1/approvals/apr_11223344/reject \
  -H "Authorization: Bearer $SERICIN_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"comment": "Amount exceeds departmental budget ceiling. Please resubmit after budget review."}'
```

<Note>
  The `comment` field is **required** when rejecting an approval request. This ensures there is always a recorded reason when an agent action is blocked, which is critical for audit trails and for helping agent owners understand why their workflow was interrupted.
</Note>

## Approval timeouts

To prevent agent workflows from stalling indefinitely, policies can include a `timeout_hours` value. If no approver submits a decision within that window, Sericin automatically rejects the request and cancels the agent action. The timeout event is recorded in the audit log the same way a manual rejection would be.

To set a timeout when creating or updating a policy, include the field in your request body:

```json
{
  "timeout_hours": 24
}
```

If you omit `timeout_hours`, approval requests wait indefinitely until an approver acts.

<Warning>
  Rejected approvals — whether rejected manually or due to a timeout — cannot be reversed. The original approval request is closed permanently. If the agent needs to retry the action, it must resubmit the action from scratch, which will create a new approval request.
</Warning>
